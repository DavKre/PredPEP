# Where "Rosetta" appears in the user interface

A map for replacing the word with another keyword. Counts are case-insensitive
and exclude the vendored bundles (`ngl.js`, `ngl.umd.js`, `plotly.min.js`), which
contain none.

| layer | hits | relevance |
|---|---|---|
| `app/templates/index.html` | 8 | 6 visible, 2 in HTML comments |
| `app/static/js/*.js` | 65 | ~35 visible, rest comments and identifiers |
| `app/static/css/style.css` | 0 | — |
| `app/*.py` | 155 | mostly paths/env; a handful reach the browser |
| `pipeline/*` | 115 | none user-visible, but owns the CSV column names |

**The important finding first:** the UI almost everywhere keeps the *display
label* separate from the *data key*. `results.js` has
`{ key: 'rosetta', label: 'Rosetta total' }`; `plots.js` has
`['interface_score', 'Interface energy']`. So **tier 1 below can be renamed on
its own, without touching a single data key, CSV header or API field.** That is
the whole job if the goal is what users read.

## Tier 2 — data contract. Do NOT rename casually.

These are keys, not prose. They are written by the pipeline, read by the app,
parsed by the browser, and **already present in every result CSV on disk**, so
renaming them breaks old jobs as well as the chain.

| name | written by | read by |
|---|---|---|
| `Rosetta_Total_Score` | `pipeline/run_mergeScores.py`, `run_catSPEC.py` | `job_analytics.py`, `results.js:206`, `plots.js:262`, `analytics.js:490` |
| `rosetta_available` | `pipeline/run_mergeScores.py` | `results.js:206` |
| `rosetta_csv_content` | `predPEP.py:1254` (`/results_data`) | `results.js:488` |
| `source: 'rosetta'` | `residue_catalogue.py:529, 572, 610` (`/api/residues`) | `residues.js` — tested, never printed |

If the keyword has to change here too, the options are, in order of safety:

1. **Map at the display layer only** — keep the keys, translate in the UI. Zero
   risk, and most of it is already done for you by the label/key split.
2. **Rename with a read-side fallback** — pipeline writes the new name, readers
   accept either, so historic CSVs keep working. Needs changes in
   `run_mergeScores.py`, `run_catSPEC.py`, `recover_ncaa_table.py`,
   `job_analytics.py`, `results.js`, `plots.js`, `analytics.js` and the 38-test
   suite, which asserts on these column names.
3. Rename outright — breaks every existing job's results view.

## Tier 3 — invisible. Leave alone unless you want churn.

Internal identifiers (`key: 'rosetta'`, `ROSETTA_DEFAULTS`, `rosettaTermFields`,
element id `rosettaDefaults`, `const ROSETTA_TERMS`), and code comments in
`residues.js`, `viewer.js`, `api.js`, `submit.js`, `results.js`. No user ever
sees these; renaming them carries risk without benefit.

Also invisible: everything under `app/*.py` and `pipeline/*` that is a path, an
env var or a binary name — `PREDPEP_ROSETTA`, `ROSETTA_ROOT`,
`/usr/local/rosetta_pkgs/...`, `rosetta_scripts.static.linuxgccrelease`,
`PREDPEP_ALLOW_ROSETTA_NCAA`. These are the real Rosetta and **must** keep their
names; they account for most of the 155 + 115 hits in those two layers.

## Scale

Doing tier 1 only: roughly **55 strings across 9 files** — `index.html`,
`results.js`, `plots.js`, `analytics.js`, `residues.js`, `submit.js`,
`console.js`, `charts.js`, plus the server strings in `predPEP.py` and
`residue_catalogue.py`. No data keys, no pipeline changes, no test changes.

One caveat worth settling before starting: the agreement chart compares two
scoring engines, so "FoldX ↔ Rosetta" becomes "FoldX ↔ *keyword*". If the aim is
to stop naming the engine, FoldX is named just as often and would need the same
treatment — there are comparable counts of "FoldX" throughout the same files.
